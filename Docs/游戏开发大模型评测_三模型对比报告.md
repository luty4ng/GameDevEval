# GPU Driven Terrain 三模型对比报告

## 摘要

本报告比较 GPT-5.6 的三个模型变体在同一份 Unity GPU Driven Terrain 提示词下的实现结果：`Luna`、`Terra` 和 `Sol`。

先给结论：

- **Sol 的端到端交付最完整**：7 级 LOD、GPU buffer、GPU 顶点生成、Autopilot 1km 运行探针、GC/贴地探针和自评表都形成了闭环证据。
- **Terra 的架构最直接、易解释**：不创建 Unity Mesh，使用 `Graphics.DrawProcedural`；视觉截图稳定，但交互和运行态验收主要停留在代码/静态检查层面。
- **Luna 的方案可运行但视觉风险最高**：采用传统 `MeshRenderer + 静态拓扑 + GPU 位移` 的 Unity 组件路径，代码结构清楚，但现有正常/远景截图有明显条带、亮缝和环带接缝问题，且 Profiler 证据不足以证明系统级 GC=0。

> 名称说明：项目与统一提示词中的实际目录是 `Luna`、`Terra`、`Sol`。本报告将用户描述中的 “Tara” 对应为项目目录 `Terra`，将 “So” 对应为 `Sol`。

## 1. 评测条件与证据边界

三套实现使用同一份任务提示词，唯一的工作区变量是 `{WORKSPACE}`：`Luna`、`Terra`、`Sol`。共同约束包括：Unity `6000.5.5f1`、URP `17.5.0`、6 级以上 clipmap、FBM 高度场、GPU 生成/更新、无逐帧 CPU Mesh 重建、第一人称相机、F1 调试视图和固定 Autopilot 路径。

统一提示词与评分标准：

- [统一任务提示词](游戏开发大模型评测_GPU驱动地形任务提示词_下发版.md)
- [完整提示词、评分 Checklist 与设计说明](游戏开发大模型评测_GPU驱动地形任务提示词.md)

本报告采用三类证据，并明确区分：

1. **实现事实**：来自 C#、Shader、Compute Shader 和 README，可通过代码复核。
2. **运行事实**：来自 Console、Profiler、运行态探针和模型自评记录。
3. **视觉事实**：来自 `Report/` 中的截图；截图只证明所捕获画面的状态，不自动等价于完整运行时验收。

证据采集时间主要为 **2026-09-12**。表格中的 `pass / partial` 保留各模型自评结论，不代表重新执行后的独立评分。

## 2. 评分模型与最终结果

### 2.1 评分算法

本报告采用加权评分，而不是直接按“通过项数量”计分。这样可以区分“功能已经实现”和“功能已经被运行证据证明”这两种不同状态。

每个维度先给出 `0–5` 的原始分数 `rᵢ`，再按该维度权重 `wᵢ` 换算为加权分：

```text
单项加权分 pᵢ = wᵢ × rᵢ / 5
最终总分 S = Σ pᵢ
```

所有权重之和为 100，因此最终得分范围为 `0–100`。原始分数的统一口径如下：

| 原始分 | 判定口径                                               |
| ------:| ------------------------------------------------------ |
| 5      | 规格满足，并有直接运行态或多重证据支撑                 |
| 4      | 实现基本满足，有代码/截图证据，但缺少部分运行态闭环    |
| 3      | 有可工作的实现方向，但只有静态证据，或存在明显未验证项 |
| 2      | 已有实现，但存在明显视觉、性能或验收风险               |
| 1      | 仅有局部实现或证据非常不足                             |
| 0      | 未实现、违反硬性约束，或现有证据显示失败               |

“视觉质量”只评价画面观感，“裂缝/边界完整性”评价几何正确性；“证据质量”评价结论是否可复核。这三个维度分别计分，避免把截图观感、技术实现和验证可信度混成一个分数。

### 2.3 分数解释

| 总分区间 | 含义                                           |
| --------:| ---------------------------------------------- |
| 90–100   | 规格实现和运行证据都较完整，可作为当前主版本   |
| 80–89    | 核心方案可靠，但仍有运行验证或性能优化缺口     |
| 70–79    | 具备可运行基线，但存在明显视觉、性能或证据风险 |
| 0–69     | 关键能力缺失，或无法用现有证据证明达到验收要求 |

### 2.4 最终排名

1. **Sol：94.8 / 100** —— 实现、运行探针和证据闭环最完整；主要扣分来自截图中的细亮线、裙边观感，以及 25 个 draw 带来的结构复杂度。
2. **Terra：81.8 / 100** —— 架构清楚、视觉表现稳定、GPU procedural 路径直接；主要扣分来自每帧全量高度 dispatch，以及交互/Autopilot/GC 没有完成独立运行态闭环。
3. **Luna：75.0 / 100** —— Unity 组件式 GPU 地形路径成立，文档和静态结构完整；主要扣分来自正常/远景截图的接缝风险、系统级 GC 证据不足和 1km 运行未完成实测。

> 以上分数是基于当前仓库中已有实现、日志、自评表和截图的“证据加权分”，不是对模型能力的绝对排名。若后续补齐运行测试或修复视觉问题，应重新计算对应维度。

## 5. Luna：传统 Unity 组件路径，视觉接缝是主要风险

### 5.1 实现概要

Luna 使用 `Luna_GpuTerrainController` 在启动时创建一个 128×128 静态网格，然后复用到 6 个 ring 上。不同 LOD 通过 Transform 的格子尺寸缩放实现，格长依次为 `1/2/4/8/16/32m`。高度场由 Compute Shader 写入 1024² 的 RFloat `RenderTexture`，Shader 顶点阶段读取高度并计算法线、morph 和调试模式。

关键实现点：

- 只在相机跨过 64m snap 格时重新 dispatch 高度纹理，不是每帧重建高度场。
- CPU 只在启动阶段创建 Mesh；运行期间未发现逐帧 `Mesh.vertices`/`SetVertices` 路径。
- 使用 6 个 `MeshRenderer`，粗环先绘制，细环通过重叠和 render queue 获取覆盖优先级。
- 第一人称相机和 Autopilot 使用 Input System，Autopilot 速度字段为 25m/s。

代码证据：[Luna_GpuTerrainController.cs](../Assets/Luna/Luna_GpuTerrainController.cs)、[Luna_FirstPersonController.cs](../Assets/Luna/Luna_FirstPersonController.cs)、[Luna_GpuTerrain.shader](../Assets/Luna/Luna_GpuTerrain.shader)。

### 5.2 视觉证据

正常视图体现了高度场和山地轮廓，但画面中心可见多条亮色/缺口状接缝；远景图能看到较明显的 ring 边界。LOD 图则能清楚显示 6 个嵌套方环，线框图也能看出近密远疏的层级结构。

建议概括为：**Luna 证明了“Unity 组件式 GPU 地形”的实现路径可行，但还没有把视觉接缝和性能测量收敛到可验收状态。**

## 6. Terra：无 Mesh 的直接 Procedural Draw，架构最容易讲清

### 6.1 实现概要

Terra 使用 `TerraGpuTerrainRenderer`，不创建 Unity Mesh，而是通过 `Graphics.DrawProcedural` 让 Shader 根据 `SV_VertexID` 展开每级 128×128 网格。6 个 LOD 共用一个 `ComputeBuffer<float>`，每级保存 129×129 高度样本。高度由 Compute Shader 的 5 octave FBM 生成，默认最大高度 110m。

关键实现点：

- LOD 格长为 `1/2/4/8/16/32m`，最外层覆盖 4096×4096m。
- 外缘使用 `smoothstep(0.74, 0.96)` morph 到父级格点，并保留一格父级间距的覆盖。
- 每个 LateUpdate 都会根据相机更新 origin、dispatch 高度计算并提交 6 个 procedural draw；实现简单，但在相机静止时仍有可优化空间。
- `Terra_FirstPersonController` 使用 CPU 镜像噪声进行贴地；Autopilot waypoint 和速度符合任务规格，但本次 MCP 未实际注入键盘操作。

代码证据：[Terra_GpuTerrainRenderer.cs](../Assets/Terra/Scripts/Terra_GpuTerrainRenderer.cs)、[Terra_FirstPersonController.cs](../Assets/Terra/Scripts/Terra_FirstPersonController.cs)、[Terra_GpuTerrainHeight.compute](../Assets/Terra/Resources/Terra_GpuTerrainHeight.compute)、[Terra_GpuTerrain.shader](../Assets/Terra/Shaders/Terra_GpuTerrain.shader)。

### 6.3 证据与风险

Terra 的自评将 A、D、F、I、J 标为 pass，将 B、C、E、G、H 标为 partial。README 中记录了全局 Profiler 的 `GC Allocated In Frame = 832B`，并注明该数值包含 Editor/MCP；同时记录了当前 MCP 无法自动发送 WASD/P，因此相机控制和 Autopilot 没有完成自动化实测。

建议概括为：**Terra 的技术方案很干净，尤其说明了“GPU 顶点生成不等于 CPU 创建 Mesh”；但它的运行态验证主要是静态证据，性能上还应把高度 dispatch 改成 dirty-only。**

## 7. Sol：最完整的 GPU clipmap 与运行态验证闭环

### 7.1 实现概要

Sol 使用 `Sol_GpuTerrainSystem`，每级 64×64 格、65×65 高度样本，共 7 级，格长从 1m 扩展到 64m。中心级使用一个完整 patch，外层每级由四个环形 patch 组成，因此总 draw 数为 `1 + 6×4 = 25`。Shader 使用 `SV_VertexID` 在 GPU 顶点阶段生成三角形与裙边，不创建 Unity Mesh。

关键实现点：

- 共用一个 29,575 元素的 GPU 高度 buffer。
- 相机按每级格长 snap；只有 origin 发生变化的 LOD 才重新 dispatch，父级移动时同步更新相关材质参数。
- 外侧 28% 过渡带执行父级格点 morph，四边生成向外、向下的裙边，覆盖独立 snap 造成的接口空隙。
- 运行期间通过 `System.GC.GetAllocatedBytesForCurrentThread()` 分别记录地形和相机线程分配。
- Autopilot 在跨 waypoint 的帧内消费剩余距离，因此不会因为跨点而损失 25m/s 的位移。

代码证据：[Sol_GpuTerrainSystem.cs](../Assets/Sol/Runtime/Sol_GpuTerrainSystem.cs)、[Sol_FirstPersonController.cs](../Assets/Sol/Runtime/Sol_FirstPersonController.cs)、[Sol_TerrainHeight.cs](../Assets/Sol/Runtime/Sol_TerrainHeight.cs)、[Sol_GpuTerrain.shader](../Assets/Sol/Resources/Sol_GpuTerrain.shader)。

## 8. 三种实现的工程取舍

### 8.1 拓扑策略

Luna 把拓扑交给 Unity Mesh，在启动阶段创建一次；Terra 和 Sol 把三角形展开交给顶点 Shader。三者都避开了“每帧 CPU 重建 Mesh”，但工程含义不同：

- **Luna**：更符合普通 Unity 场景/组件心智模型，调试入口自然，但 MeshRenderer、ring overlap 和深度排序更容易把接缝问题带到画面中。
- **Terra**：结构最简，6 次 draw 就能表达 6 个 LOD；但每帧都 dispatch 六级高度场，更新策略还不够节制。
- **Sol**：把环带 patch、morph、裙边都显式建模，复杂度最高；相应地，边界处理和运行态探针也最完整。

### 8.2 高度数据更新策略

这是三套实现最有代表性的差异：

```text
Luna:  相机跨 64m snap → 重算 1024² RenderTexture → 6 个 ring 采样
Terra: 每个 LateUpdate → dispatch 6 个 LOD → 6 次 procedural draw
Sol:   只有 dirty LOD → dispatch 对应 65² buffer → 25 个预配置 draw
```

Luna 的高度纹理容量大、采样方式直观，但单张纹理对边界和环带管理要求高；Terra 的实现最容易理解，但还有明显的 dispatch 优化空间；Sol 的增量更新最符合“相机移动驱动 clipmap”的运行时模型，不过 25 个 draw 和裙边几何会增加渲染组织复杂度。

### 8.3 验证闭环

同一提示词下，三套结果的差异不只在代码，也在“是否把自检做完”：

1. Luna 有 Console 记录和多种截图，但 1km、系统级 GC 和裂缝测试不完整。
2. Terra 有稳定的静态视觉证据，但 MCP 没有完成实际 WASD/P 交互注入。
3. Sol 追加了组件分配、贴地误差、Autopilot 速度和 1km 运行探针，所以更接近可审计交付。

这说明对于图形/引擎类任务，**实现方案和验证方案同等重要**：同样满足代码层面的约束，运行态证据质量仍然会显著改变最终可信度。

## 9. 结果展示建议

推荐按下面顺序讲，控制在 5–8 分钟：

1. **先讲统一约束**：同一 Prompt、同一 Unity/URP 环境，只有工作区名称不同。
2. **再讲架构分歧**：Luna 是 MeshRenderer ring；Terra 是 DrawProcedural；Sol 是 RenderPrimitives + patch/skirt。
3. **展示三组 LOD/线框截图**：说明三者都确实做了 GPU clipmap，而不是只生成了一块静态地形。
4. **展示验证差异**：强调 Sol 有 `groundError=0`、`alloc=0` 和 Autopilot 速度/1km 记录；同时诚实说明 Luna/Terra 的 partial 来源。
5. **最后讲工程判断**：推荐 Sol 作为当前最完整结果，Terra 作为最易维护的基线，Luna 作为需要继续修复接缝和性能证据的 Unity 集成方案。

不要把以下结论说得过满：

- “截图没有裂缝”——Luna 明显不应这样说，Sol 也应先处理细亮线。
- “Profiler 已证明每帧 GC=0”——Luna/Terra 的全局 Editor/MCP 读数并不能证明这一点。
- “Autopilot 已经完整手测”——Terra 的自评明确记录没有自动发送 P 键；Luna 也没有完成 1km 实际计时。

## 11. 最终结论

在这次同题对比中，**Sol 的优势不是单一技术点，而是“实现、运行验证、证据记录”三者同时闭环**。Terra 说明了更简单的 procedural draw 基线如何快速达到可视化结果；Luna 说明了传统 Unity 组件路径如何接入 GPU 地形，但也暴露出环带接缝和性能测量的工程风险。

如果需要把其中一套继续打磨成现场演示版本，优先顺序建议是：

1. 以 Sol 作为主展示版本，先修复正常/远景截图中的细亮线并补一张无接缝的回归截图。
2. 保留 Terra 作为“简洁架构对照组”，把每帧全量 dispatch 改成按 snap dirty 更新。
3. Luna 继续定位 ring overlap、height texture 边界和深度排序造成的视觉接缝，并使用 Player Profiler 补齐系统级 GC 证据。
