# 游戏开发场景下三模型对比评测：提示词与评测设计指导性文档

> 适用场景：笔试/作业交付文档。目标是对比三个不同大模型在同一游戏开发任务上的表现，并给出可复现、可辩护的评测结论。

---

## 一、先明确评测的顶层原则

在设计任何提示词之前，先确立四条原则，它们决定了后续所有设计决策：

1. **同题同条件（Fair Comparison）**：三个模型必须使用完全相同的任务描述、上下文输入、输出格式要求和解码参数（temperature、top_p、max_tokens）。模型之间的差异只能来自模型本身，不能来自提示词或参数的差异。业界通用评测体系的共识是"用同一提示词对比不同模型的完成度、响应效率与幻觉控制"。
2. **程序验证优先于主观打分**：能跑测试、能编译、能运行的检查，绝不用 LLM 主观判断替代。只有无法程序化验证的维度（如设计合理性、代码可读性）才交给 LLM-as-a-Judge。
3. **多次重复，分清"稳定性"与"方差"**：单跑一次的结果不构成证据，每个任务至少跑 3 次。但必须写清楚：temperature=0 下三次运行理论上应当一致，重复运行实际检验的是推理服务非确定性带来的**稳定性**（主流 API 即使 temp=0 也不保证逐位复现）；估计采样方差必须在 temp>0 下多采样。两种口径二选一并写进报告（方案见 3.3）。
4. **结果可复现**：记录模型精确版本号、API 参数、时间戳、完整 prompt 与输出。评测 prompt 本身纳入版本管理。

## 二、任务设计：游戏开发任务的分层

不要只设计一个"大而全"的任务。建议设计 **3~5 个梯度任务**（task ladder），从封闭到开放，这样对比才有区分度：

| 层级 | 任务类型 | 示例 | 主要考察能力 |
|---|---|---|---|
| L1 封闭 | 代码补全/单函数实现 | 实现 Unity 中基于四叉树的碰撞检测函数，附函数签名 | 语法正确性、API 熟悉度 |
| L2 半封闭 | 特性实现 | 给一段现有玩家控制器代码，实现"二段跳 + 土狼时间" | 对现有代码的理解、需求遵循 |
| L3 半开放 | Bug 定位与修复 | 给一段有确定性 bug 的 ECS 系统代码（如事件监听泄漏），要求定位并修复 | 调试推理、因果分析 |
| L4 开放 | 系统设计 | 设计一个 10 万同时在线 MMO 的背包系统服务端架构 | 架构权衡、领域知识、表达 |
| L5 开放+迭代 | 多轮修改 | 在 L2 基础上追加"要求兼容手柄输入"的 follow-up | 上下文保持、增量修改能力 |
| L6 反馈修复（可选） | 错误反馈驱动迭代 | 把 L2/L3 首轮输出的编译错误/测试失败信息喂回同一模型，允许再修 2 轮 | 从编译器/测试反馈中定位并修复问题的能力 |

这种分层设计借鉴了 MT-Bench 的多轮思想（第二轮检验 follow-up 能力），同时覆盖了从"可程序验证"到"必须主观评判"的完整光谱。

**为什么建议加 L6（或至少声明其缺席）**：2025-2026 年主流工程评测（SWE-bench、GameDevBench）都是 agent 式的——给仓库/工程，模型带工具多轮迭代；真实开发中的用法也是"生成 → 编译 → 报错 → 修复"的循环。模型在单轮生成下的排名与在迭代修复下的排名**可能不一致**：GameDevBench 中给 agent 喂回图像/视频反馈，成功率从 41.1% 提升到 52.0%——利用反馈修复的能力本身就是模型间差异的来源。两条路：把 L6 纳入对比，或在报告局限性中明确声明"结论限于单轮生成，不外推到带工具的 agent 工作流"。

**任务设计注意点：**
- 题目尽量取自真实业务场景或自行构造，避免直接使用公开 benchmark 原题（防止数据污染——模型可能在预训练中见过标准答案，排行榜分数只能作为能力上界参考）。污染防控要落到可操作的动作，不只是"不用原题"：
  1. **等价改写自检**：把自造题做一次语义等价改写（换数值、换命名、换场景皮肤、保持考察点与难度），再测一轮。改写后通过率明显下降，说明题目存在软污染——知识迁移比原文泄漏更隐蔽（公开代码基准的改写版实验中，顶部模型掉了 19-29%）。
  2. **教程改编要重度改写**：任务灵感取自公开教程/文档时（GameDevBench 的任务即改编自网页与视频教程），只保留考察点结构，换掉引擎版本、API 选择与需求细节，否则模型可能"背过教程"。
  3. **排行榜只作参考**：连 OpenAI 都因污染与测试缺陷弃用了 SWE-bench Verified；静态基准分数只能作为能力上界参考。
- 每个任务写清楚**输入、期望输出、验收标准**三部分，验收标准在设计任务时就定好，不要在看到模型输出后再改标准（避免 Goodhart 定律：指标变成目标后就不再是好指标）。

## 三、被测模型的提示词设计规范（核心交付物）

### 3.1 结构骨架

给三个模型用的任务提示词，统一采用以下结构（每个部分用空行/分隔符隔开，指令与参考代码用三引号或代码块隔离，防止指令冲突）：

```
【角色】
你是一名资深游戏客户端/服务端工程师，熟悉 Unity (C#) / Unreal (C++) 与常见游戏架构。

【上下文】
<项目背景 2-4 句；如需贴现有代码，用 ``` 代码块包裹>

【任务】
<明确、单一、可验收的需求描述>

【约束条件】
- 使用的引擎/API 版本：...
- 禁止使用的特性：...
- 性能要求（如：不得在每帧产生 GC 分配）：...
- 代码风格要求（命名、注释密度）：...

【输出格式】
- 只输出完整可编译的代码文件（或：先输出设计说明，再输出代码）
- 代码中关键决策处添加简短注释
- 如有无法实现的约束，显式说明原因，不要静默忽略

【验收标准】
1. 代码可通过编译（无语法错误、引用完整）
2. 满足上述全部约束条件
3. <任务特有的功能性标准，如"土狼时间窗口为 0.1s 且参数可配置">
```

### 3.2 设计要点逐条说明

1. **角色设定适度即可。** 角色提示能改变输出风格和稳定性，但"资深工程师"已足够，堆砌过多形容词没有收益，反而引入噪声。
2. **约束条件必须显式、可判定。** "性能好"不是约束，"Update 中不允许 new 对象/不允许 FindGameObject 调用"才是约束。模糊约束会给 LLM-as-Judge 的打分带来分歧。
3. **输出格式要强约束 + 给退路。** 要求"只输出代码"能方便程序化处理，但必须允许模型声明约束冲突（否则它可能用幻觉硬凑）。要求关键决策注释，是为了让评审能区分"运气写对"和"理解正确"。
4. **验收标准直接写进提示词。** 这既是给模型的自查清单，也自然成为后续评分的 rubric 来源，保证"出题标准"与"评分标准"一致。
5. **Zero-shot 为主，Few-shot 慎用。** 统一用 zero-shot（只给任务不给示例），保证公平且省事。若用 few-shot，则三个模型必须用同一套示例，且示例会在主观评判时引入锚定——笔试场景建议直接 zero-shot，把"格式遵循能力"本身作为考察点。
6. **控制 token 与格式噪音。** 提示词保持 500 词以内、结构清晰；超长提示词会导致模型忽略前文指令。
7. **语言统一。** 三个模型统一用中文（或统一用英文）出题，不要混用——语言本身会影响代码模型的表现。

### 3.3 参数设置

- temperature = 0（或各模型 API 允许的最低值），消除采样随机性，凸显能力差异；
- 记录 top_p、max_tokens、system prompt 有无；
- 若某模型不支持 temperature=0，在报告中如实披露该差异。

**temp=0 与"跑 3 次"的关系必须写清楚**。temp=0 并不保证逐位复现——MoE 路由、浮点归约、服务端批处理都会引入非确定性（厂商 API 文档对此也只承诺"尽量确定"）。所以 temp=0 下重复 3 次的真实作用是**稳定性检查**，不是方差估计。两种自洽的设计，二选一并写进报告：

| 方案 | 设置 | 报什么 | 适合 |
|---|---|---|---|
| 一（推荐）：公平性优先 | temp=0，每任务跑 3 次 | 每任务 3 次运行的一致性分布（3/3、2/3、0/3 通过） | 笔试对比，排除采样随机性 |
| 二：真实使用优先 | temp≈0.7，每任务采样 5 次 | pass@1 均值 ± 标准差 | 想反映真实调用波动 |

指标命名注意：pass@k（k 次中至少一次通过）与 pass^k（k 次全部通过，衡量可靠性）含义不同。2025 年的研究指出 pass@k 的模型排名不稳定，agent 场景的通行做法是报 Best@k 并披露尝试次数；本文档方案一报的"3 次一致性分布"本质上就是可靠性口径。

## 四、评估方法：客观验证 + 主观评判的双轨制

游戏开发任务的输出天然适合"客观为主、主观为辅"的混合评测（这也是 V-GameGym、RPG Bench、GameDevBench 等游戏向评测的工作范式：客观 checker 提供稳定比较基准，主观维度补充质量判断）。游戏开发区别于普通代码评测的一点是**视觉正确性**：GameDevBench 中模型在玩法类任务通过率 51.4%，在 2D 图形类任务骤降至 33.0%——"能编译、测试全绿"不等于"画面看起来对"。因此本框架把运行时视觉验证纳入双轨（见 4.1/4.2）。

### 4.1 客观验证层

权重按任务层级分配，不要全卷面套一个统一比例：L1-L3 客观为主（建议占总分 60-70%）；L4-L5 客观项少（只有约束违规、格式类检查），建议占 20-30%，其余让给主观层。

| 指标 | 适用任务 | 验证方式 |
|---|---|---|
| 编译通过率 | L1-L3 | 放入对应引擎/编译环境实际编译 |
| 功能测试通过率 | L1-L3 | 预先编写的单元测试 / 运行期断言（如 PlayMode 测试） |
| 约束违规数 | 全部 | 静态检查脚本（如统计 Update 中的 GC 分配 API 调用） |
| 差分测试 | L3 | 修复后跑原 failing 用例，必须转绿 |
| 运行时视觉断言 | L2-L3、L5 | 脚本化采集运行期截图/录屏 + 可程序判定的断言（UI 元素存在、对象位置在预期范围、关键帧渲染非空） |

### 4.2 主观评判层：LLM-as-a-Judge + 人工抽查（L1-L3 建议占总分 30-40%；L4-L5 占 70-80%）

对无法程序化的维度，用"强模型做评委 + rubric 打分"：

**评委选择**：选一个不属于被测三模型之列的更强模型做评委（避免 self-preference 偏差——模型给自己/自家输出打分偏高是已证实的偏差）。

**多模态视觉评委（游戏开发特有，L2-L3、L5 必做）**：把 4.1 采集的运行期截图/录屏连同任务要求一起交给多模态模型，评"视觉正确性"（UI 摆放、动画时序、特效触发是否符合预期）——V-GameGym 的做法就是"代码 + 视觉渲染 + 玩法功能"的三维评测管线；GameDevBench 的数据（玩法 51.4% vs 2D 图形 33.0%）也说明视觉维度是模型最容易翻车、最值得单独评的地方。注意：截图采集条件必须脚本化固定（同一测试场景、同一帧号、同一分辨率），否则视觉评委会把渲染环境差异误判成模型差异。

**人工抽查（L4-L5 必做）**：架构方案没有唯一解，由人按设计要素表勾选（是否考虑了扩容、持久化、一致性、失败恢复等）；该层同时产出评委校准用的人工标注样本（见下方校准条目）。

**Rubric 设计规范**（每个维度给 1-5 分锚点描述）：

| 维度 | 定义 | 低分锚点 (1) | 高分锚点 (5) |
|---|---|---|---|
| 需求遵循（checklist 化） | 是否完整实现任务需求，无遗漏无超范围 | 缺失核心需求 | 全部满足且边界情况有处理 |
| 领域正确性 | 引擎 API / 游戏机制理解是否正确 | 出现臆造的 API 或错误机制 | API 使用地道，符合引擎最佳实践 |
| 代码质量 | 可读性、结构、可维护性 | 面条代码、命名混乱 | 职责清晰、抽象适度 |
| 设计权衡（仅 L4/L5） | 方案取舍的合理性与论证 | 无论证堆砌 buzzword | 明确列出 trade-off 并给出取舍理由 |
| 指令遵循（checklist 化） | 输出格式/约束的遵守程度 | 格式混乱 | 完全遵守 |

**Rubric 设计注意事项：**
- **能 checklist 化的维度不打数值分。** 2025 年业界实践的共识是细粒度数值分数不可靠（实测存在平台期、不连续跳变，且随评委模型更换发生尺度漂移），布尔/分类判定的一致性显著更高。据此：**需求遵循、指令遵循**两个维度改为把提示词里的验收标准与约束条件展开成逐条 pass/partial/fail 的 checklist，统计通过率与违规数——出题时验收标准已写进提示词，这里直接复用，天然保证"出题标准 = 评分标准"且完全可判定；**领域正确性、代码质量、设计权衡**是真正连续的维度，保留锚点打分。
- 维度控制在 4-6 个，且彼此正交。研究发现 rubric 维度之间可能存在隐性耦合（"简洁"和"切题"经常同涨同落），导致重复计分、扭曲总分——设计后可用小样本预跑检查各维度得分相关性，相关性过高（如 r>0.8）的维度应合并或删除。
- 保留打分的维度给出 1/3/5 三档行为锚点描述（行为锚定量表），比"1-5 分，5 分最好"这类空泛说明的评分一致性显著更高。
- 评分时要求评委**先输出分析理由再给分**（chain-of-thought 式评判，G-Eval 的做法），打分可靠性更高。

**Judge 提示词模板**（checklist + 锚点双段式）：

```
你是一名严格的游戏开发技术评审。请评审以下代码/方案。

【原始任务】
{任务描述原文，含验收标准与约束条件}

【被评审输出】
{模型输出}

【第一部分：Checklist 逐条判定】
对下列每一条输出 "pass" / "partial" / "fail"，并引用代码中的具体证据：
1. {验收标准逐条展开}
2. {约束条件与输出格式要求逐条展开}

【第二部分：锚点评分】（逐维输出：分析理由 → 分数 1-5，依据锚点定义）
- 领域正确性：出现臆造 API/错误机制(1) ←→ API 地道、符合引擎最佳实践(5)
- 代码质量：面条代码、命名混乱(1) ←→ 职责清晰、抽象适度(5)
- 设计权衡（仅 L4/L5）：无论证堆砌 buzzword(1) ←→ 明确列出 trade-off 并给出取舍理由(5)

【输出格式】JSON：
{"checklist": [{"item": 1, "verdict": "pass|partial|fail", "evidence": "..."}],
 "scores": {"领域正确性": {"reasoning": "...", "score": N}, "代码质量": {"reasoning": "...", "score": N}}}

注意：
- 只依据任务描述与锚点定义判定，不要受回答长度、排版美观影响
- 发现 API 幻觉（臆造不存在的引擎接口）时：对应 checklist 条目判 fail，且领域正确性 ≤2 分
```

**评委偏差控制清单：**
- **位置偏差**（pairwise 对比时偏好先出现者）：如果做 A/B 两两对比，必须交换顺序各评一次，两次结果不一致记为 tie；
- **冗长偏差**（偏好更长回答）：rubric 中显式声明"分数与篇幅无关"，并在 reason 中要求引用具体证据；
- **自我偏好**：评委不得为被测三模型之一或其同家族小版本；
- 评委温度设为 0，同一输出评 2 次取一致者（或取均值）；
- 评委校准：用 20-30 条人工标注样本（覆盖明显好、明显差、人类内部有分歧三类）校验评委与人工判断的一致率，一致率 75%-90% 说明评委基本可用；报告机会校正后的 Cohen's kappa 而非裸百分比（好/坏样本占比极端时裸一致率会虚高），并以人类标注员之间的一致率为天花板（评委"超过"人类一致率反而可疑）。两条经验规则：两个标注员一致率 <80% 说明题目或 rubric 定义有歧义，先修定义再修评委；一致率达标仍要抽查混淆矩阵——评委可能在恰好你最在意的失败模式上漏报。

## 五、实验流程与记录规范

1. **准备阶段**：定任务（附验收标准）→ 写测试/检查脚本 → 写评审 rubric → 小规模预跑（检查题目本身无歧义、脚本可用）。
2. **执行阶段**：三模型 × N 任务 × 3 次重复（temperature=0，重复作为稳定性检查，口径见 3.3），完整落盘输入输出；有可运行输出的任务（L2-L3、L5）同步脚本化采集运行期截图/录屏。
3. **评分阶段**：先跑客观验证脚本（编译/测试/静态检查/视觉断言），汇总通过率；再统一送评委按 checklist + rubric 打分（文本评委 + 视觉评委，同一批输出打乱顺序、隐藏模型身份——盲评）。
4. **分析阶段**：
   - 总表：模型 × 任务 × 维度 的得分矩阵；
   - 客观指标：各任务 3 次运行的一致性分布（3/3、2/3、0/3 通过）；采用方案二时报 pass@1 均值 ± 标准差（见 3.3）；
   - 主观指标：各维度均值 + 评委间一致率；
   - **模型总分与排名（必交付）**：按 4.1/4.2 的分层权重加权汇总出各模型总分并排名；分差小于运行间波动时如实写"无法区分"，允许并列；
   - **强弱差距量化（必交付）**：最强与最弱模型的差距要落到数字和来源——总分差多少、按维度分解（差距主要来自编译通过率还是代码质量）、按任务层级分解（封闭题还是开放题拉开差距）；分差要对照重复运行波动与评委一致率判断是否超出噪声，小样本不用"显著"措辞；
   - **能力剖面**：模型 × 维度 的热力图/雷达图，直观回答"谁强在哪、弱在哪"（如"模型 A 客观项全过但代码质量分垫底"）；
   - 定性分析：挑 2-3 个典型案例（最佳/最差/最具分歧）做输出对比分析——这是笔试文档里最出彩的部分，展示你"读懂了输出"而不只是"跑了分"。
5. **结论（四件套，缺一不可）**：
   - 各模型总分与排名；
   - 强弱差距的量化表述（分差 + 维度/任务来源分解，见分析阶段）；
   - 按场景给推荐（如"代码补全类任务选 X，系统设计类任务选 Y"）；
   - 诚实说明局限（样本量、评委偏差、任务覆盖面；未做 L6 时必须声明"结论限于单轮生成，不外推到 agent 工作流"）。

## 六、常见陷阱速查

| 陷阱 | 表现 | 对策 |
|---|---|---|
| 数据污染 | 模型"秒答"公开原题 | 自造/改造题目，不用原题；灵感取自教程要重度改写 |
| 软污染漏检 | 原题分高、等价改写后明显掉分 | 改写自检：语义等价改写重测一轮对比（见 二） |
| 评委长度偏差 | 长篇低质代码得分反高 | rubric 显式声明、盲评 |
| 评委位置偏差 | pairwise 总偏好 A 或先出现者 | 交换顺序双评 |
| 细粒度打分漂移 | 数值分数有平台期/不连续跳变，换评委模型后整体漂移 | 可判定维度 checklist 化（pass/fail），只给连续维度留锚点分 |
| 评委校准虚高 | 裸一致率达标但漏报关键失败模式 | 报 Cohen's kappa，抽查混淆矩阵漏报（见 4.2） |
| 维度耦合 | 各维度得分几乎相同 | 小样本预跑，查相关矩阵，合并高相关维度 |
| 改标准凑结论 | 看完输出再调 rubric | rubric 在跑实验前冻结并记录版本 |
| temp=0 被当完全确定 | 三次运行结果不一致，误以为实验出错 | 服务端非确定性是常态，重复运行本就是稳定性检查（见 3.3） |
| 单次采样当结论 | 某模型一次翻车被全盘否定 | ≥3 次重复；temp=0 下报一致性分布，temp>0 下报均值±方差 |
| 单轮结果外推到 agent | 迭代修复场景的模型排名与单轮不一致 | 加 L6，或在局限中声明不外推（见 二） |
| 视觉翻车被漏检 | 编译测试全绿但 UI/画面错误 | 运行期截图/录屏 + 视觉评委（见 4.1/4.2） |
| 忽略无效输出 | 模型输出无法编译被直接跳过 | 无法编译本身计 0 分，如实统计 |
| 只报推荐不报差距 | 结论只有"选 X"，说不清领先多少、领先在哪 | 交付总分 + 排名 + 分差量化与来源分解（见 五） |

## 参考来源（方法论文献与行业实践）

- G-Eval: rubric 驱动 + CoT 理由的 LLM-as-Judge 范式（Liu et al., 2023）
- MT-Bench 评委偏差研究：长度、位置、自我偏好偏差（Zheng et al., 2023）
- pass 指标讨论 (2025): "Don't Pass@k" 指出 pass@k 排名不稳定；SWE-bench 官方实验规范在 agent 场景报 Best@k 并披露尝试次数；pass^k（k 次全通过率）衡量可靠性
- RADAR (2026): rubric 维度行为耦合诊断，预检评分体系
- V-GameGym (上海 AI Lab, 2025): 游戏开发代码生成的客观+主观混合评测管线，强调可玩性、视觉表现等游戏特有指标
- GameDevBench (2026): 游戏开发 agent 评测基准（333 个任务，改编自网页/视频教程）；玩法任务通过率 51.4% vs 2D 图形任务 33.0%，图像/视频反馈可将 agent 成功率从 41.1% 提升到 52.0%
- RPG Bench (2025): 游戏相关评测中客观 checker 提供稳定基准、主观维度方差大的结论
- 基准污染研究：OpenAI 因污染与测试缺陷弃用 SWE-bench Verified (2025)；公开代码基准的改写版实验中顶部模型掉 19-29%（软污染证据）
- HalluLens: benchmark 设计准则——真实场景代表性、稳定性与敏感性、可复现性、抗污染
- LangChain / Arize / DeepEval 工程实践：程序化验证优先、golden dataset 校验评委（75-90% 一致率，报 Cohen's kappa）、轨迹级评估；Arize 实测细粒度数值分数不可靠，推荐布尔/分类标签
- 华为云盘古提示词最佳实践：结构化提示词、引号隔离参考文本防指令冲突
