# 游戏开发场景下三模型对比评测：提示词与评测设计指导性文档

> 适用场景：笔试/作业交付文档。目标是对比三个不同大模型在同一游戏开发任务上的表现，并给出可复现、可辩护的评测结论。

---

## 一、先明确评测的顶层原则

在设计任何提示词之前，先确立四条原则，它们决定了后续所有设计决策：

1. **同题同条件（Fair Comparison）**：三个模型必须使用完全相同的任务描述、上下文输入、输出格式要求和解码参数（temperature、top_p、max_tokens）。模型之间的差异只能来自模型本身，不能来自提示词或参数的差异。业界通用评测体系的共识是"用同一提示词对比不同模型的完成度、响应效率与幻觉控制"。
2. **程序验证优先于主观打分**：能跑测试、能编译、能运行的检查，绝不用 LLM 主观判断替代。只有无法程序化验证的维度（如设计合理性、代码可读性）才交给 LLM-as-a-Judge。
3. **多次采样估计方差**：单跑一次的结果不构成证据。每个任务至少跑 3 次（pass@1 均值 + 标准差），报告中同时给出成功率和稳定性。
4. **结果可复现**：记录模型精确版本号、API 参数、时间戳、完整 prompt 与输出。评测 prompt 本身纳入版本管理。

---

## 二、任务设计：游戏开发任务的分层

不要只设计一个"大而全"的任务。建议设计 **3~5 个梯度任务**（task ladder），从封闭到开放，这样对比才有区分度：

| 层级 | 任务类型 | 示例 | 主要考察能力 |
|---|---|---|---|
| L1 封闭 | 代码补全/单函数实现 | 实现 Unity 中基于四叉树的碰撞检测函数，附函数签名 | 语法正确性、API 熟悉度 |
| L2 半封闭 | 特性实现 | 给一段现有玩家控制器代码，实现"二段跳 + 土狼时间" | 对现有代码的理解、需求遵循 |
| L3 半开放 | Bug 定位与修复 | 给一段有确定性 bug 的 ECS 系统代码（如事件监听泄漏），要求定位并修复 | 调试推理、因果分析 |
| L4 开放 | 系统设计 | 设计一个 10 万同时在线 MMO 的背包系统服务端架构 | 架构权衡、领域知识、表达 |
| L5 开放+迭代 | 多轮修改 | 在 L2 基础上追加"要求兼容手柄输入"的 follow-up | 上下文保持、增量修改能力 |

这种分层设计借鉴了 MT-Bench 的多轮思想（第二轮检验 follow-up 能力），同时覆盖了从"可程序验证"到"必须主观评判"的完整光谱。

**任务设计注意点：**
- 题目尽量取自真实业务场景或自行构造，避免直接使用公开 benchmark 原题（防止数据污染——模型可能在预训练中见过标准答案，排行榜分数只能作为能力上界参考）。
- 每个任务写清楚**输入、期望输出、验收标准**三部分，验收标准在设计任务时就定好，不要在看到模型输出后再改标准（避免 Goodhart 定律：指标变成目标后就不再是好指标）。

## 三、被测模型的提示词设计规范（核心交付物）

### 3.1 结构骨架

给三个模型用的任务提示词，统一采用以下结构（每个部分用空行/分隔符隔开，指令与参考代码用三引号或代码块隔离，防止指令冲突）：

```
【角色】
你是一名资深游戏客户端/服务端工程师，熟悉 Unity (C#) / Unreal (C++) 与常见游戏架构。

【上下文】
<项目背景 2-4 句；如需贴现有代码，用 ``` 代码块包裹>

【任务】
<明确、单一、可验收的需求描述>

【约束条件】
- 使用的引擎/API 版本：...
- 禁止使用的特性：...
- 性能要求（如：不得在每帧产生 GC 分配）：...
- 代码风格要求（命名、注释密度）：...

【输出格式】
- 只输出完整可编译的代码文件（或：先输出设计说明，再输出代码）
- 代码中关键决策处添加简短注释
- 如有无法实现的约束，显式说明原因，不要静默忽略

【验收标准】
1. 代码可通过编译（无语法错误、引用完整）
2. 满足上述全部约束条件
3. <任务特有的功能性标准，如"土狼时间窗口为 0.1s 且参数可配置">
```

### 3.2 设计要点逐条说明

1. **角色设定适度即可。** 角色提示能改变输出风格和稳定性，但"资深工程师"已足够，堆砌过多形容词没有收益，反而引入噪声。
2. **约束条件必须显式、可判定。** "性能好"不是约束，"Update 中不允许 new 对象/不允许 FindGameObject 调用"才是约束。模糊约束会给 LLM-as-Judge 的打分带来分歧。
3. **输出格式要强约束 + 给退路。** 要求"只输出代码"能方便程序化处理，但必须允许模型声明约束冲突（否则它可能用幻觉硬凑）。要求关键决策注释，是为了让评审能区分"运气写对"和"理解正确"。
4. **验收标准直接写进提示词。** 这既是给模型的自查清单，也自然成为后续评分的 rubric 来源，保证"出题标准"与"评分标准"一致。
5. **Zero-shot 为主，Few-shot 慎用。** 统一用 zero-shot（只给任务不给示例），保证公平且省事。若用 few-shot，则三个模型必须用同一套示例，且示例会在主观评判时引入锚定——笔试场景建议直接 zero-shot，把"格式遵循能力"本身作为考察点。
6. **控制 token 与格式噪音。** 提示词保持 500 词以内、结构清晰；超长提示词会导致模型忽略前文指令。
7. **语言统一。** 三个模型统一用中文（或统一用英文）出题，不要混用——语言本身会影响代码模型的表现。

### 3.3 参数设置

- temperature = 0（或各模型 API 允许的最低值），消除采样随机性，凸显能力差异；
- 记录 top_p、max_tokens、system prompt 有无；
- 若某模型不支持 temperature=0，在报告中如实披露该差异。

## 四、评估方法：客观验证 + 主观评判的双轨制

游戏开发任务的输出天然适合"客观为主、主观为辅"的混合评测（这也是 V-GameGym、RPG Bench 等游戏向评测的工作范式：客观 checker 提供稳定比较基准，主观维度补充质量判断）。

### 4.1 客观验证层（占比建议 60-70%）

| 指标 | 适用任务 | 验证方式 |
|---|---|---|
| 编译通过率 | L1-L3 | 放入对应引擎/编译环境实际编译 |
| 功能测试通过率 | L1-L3 | 预先编写的单元测试 / 运行期断言（如 PlayMode 测试） |
| 约束违规数 | 全部 | 静态检查脚本（如统计 Update 中的 GC 分配 API 调用） |
| 差分测试 | L3 | 修复后跑原 failing 用例，必须转绿 |
| 可玩性/有效性检查 | L4-L5 | 设计评分表由专家人工勾选（架构方案没有唯一解） |

### 4.2 主观评判层：LLM-as-a-Judge（占比建议 30-40%）

对无法程序化的维度，用"强模型做评委 + rubric 打分"：

**评委选择**：选一个不属于被测三模型之列的更强模型做评委（避免 self-preference 偏差——模型给自己/自家输出打分偏高是已证实的偏差）。

**Rubric 设计规范**（每个维度给 1-5 分锚点描述）：

| 维度 | 定义 | 低分锚点 (1) | 高分锚点 (5) |
|---|---|---|---|
| 需求遵循 | 是否完整实现任务需求，无遗漏无超范围 | 缺失核心需求 | 全部满足且边界情况有处理 |
| 领域正确性 | 引擎 API / 游戏机制理解是否正确 | 出现臆造的 API 或错误机制 | API 使用地道，符合引擎最佳实践 |
| 代码质量 | 可读性、结构、可维护性 | 面条代码、命名混乱 | 职责清晰、抽象适度 |
| 设计权衡（仅 L4/L5） | 方案取舍的合理性与论证 | 无论证堆砌 buzzword | 明确列出 trade-off 并给出取舍理由 |
| 指令遵循 | 输出格式/约束的遵守程度 | 格式混乱 | 完全遵守 |

**Rubric 设计注意事项：**
- 维度控制在 4-6 个，且彼此正交。研究发现 rubric 维度之间可能存在隐性耦合（"简洁"和"切题"经常同涨同落），导致重复计分、扭曲总分——设计后可用小样本预跑检查各维度得分相关性，相关性过高（如 r>0.8）的维度应合并或删除。
- 每个维度给出 1/3/5 三档行为锚点描述（行为锚定量表），比"1-5 分，5 分最好"这类空泛说明的评分一致性显著更高。
- 评分时要求评委**先输出分析理由再给分**（chain-of-thought 式评判，G-Eval 的做法），打分可靠性更高。

**Judge 提示词模板**：

```
你是一名严格的游戏开发技术评审。请评审以下代码/方案。

【原始任务】
{任务描述原文}

【被评审输出】
{模型输出}

【评审维度】（逐维输出：分析理由 → 分数 1-5）
1. 需求遵循：...
2. 领域正确性：...
3. 代码质量：...
4. 设计权衡：...
5. 指令遵循：...

【输出格式】JSON：{"维度名": {"reasoning": "...", "score": N}, ...}

注意：
- 只依据上述锚点定义打分，不要受回答长度、排版美观影响
- 发现 API 幻觉（臆造不存在的引擎接口）时，领域正确性直接 ≤2 分
```

**评委偏差控制清单：**
- **位置偏差**（pairwise 对比时偏好先出现者）：如果做 A/B 两两对比，必须交换顺序各评一次，两次结果不一致记为 tie；
- **冗长偏差**（偏好更长回答）：rubric 中显式声明"分数与篇幅无关"，并在 reason 中要求引用具体证据；
- **自我偏好**：评委不得为被测三模型之一或其同家族小版本；
- 评委温度设为 0，同一输出评 2 次取一致者（或取均值）；
- 有条件的话用 20-30 条人工标注样本校验评委与人工判断的一致率，75%-90% 的一致性才说明评委可用。

## 五、实验流程与记录规范

1. **准备阶段**：定任务（附验收标准）→ 写测试/检查脚本 → 写评审 rubric → 小规模预跑（检查题目本身无歧义、脚本可用）。
2. **执行阶段**：三模型 × N 任务 × 3 次重复，temperature=0，完整落盘输入输出。
3. **评分阶段**：先跑客观验证脚本，汇总通过率；再统一送评委按 rubric 打分（同一批输出打乱顺序、隐藏模型身份——盲评）。
4. **分析阶段**：
   - 总表：模型 × 任务 × 维度 的得分矩阵；
   - 客观指标：pass@1 均值、标准差；
   - 主观指标：各维度均值 + 评委间一致率；
   - 定性分析：挑 2-3 个典型案例（最佳/最差/最具分歧）做输出对比分析——这是笔试文档里最出彩的部分，展示你"读懂了输出"而不只是"跑了分"。
5. **结论**：按场景给推荐（如"代码补全类任务选 X，系统设计类任务选 Y"），并诚实说明局限（样本量、评委偏差、任务覆盖面）。

## 六、常见陷阱速查

| 陷阱 | 表现 | 对策 |
|---|---|---|
| 数据污染 | 模型"秒答"公开原题 | 自造/改造题目，不用原题 |
| 评委长度偏差 | 长篇低质代码得分反高 | rubric 显式声明、盲评 |
| 评委位置偏差 | pairwise 总偏好 A 或先出现者 | 交换顺序双评 |
| 维度耦合 | 各维度得分几乎相同 | 小样本预跑，查相关矩阵，合并高相关维度 |
| 改标准凑结论 | 看完输出再调 rubric | rubric 在跑实验前冻结并记录版本 |
| 单次采样当结论 | 某模型一次翻车被全盘否定 | ≥3 次重复，报均值±方差 |
| 忽略无效输出 | 模型输出无法编译被直接跳过 | 无法编译本身计 0 分，如实统计 |

## 参考来源（方法论文献与行业实践）

- G-Eval: rubric 驱动 + CoT 理由的 LLM-as-Judge 范式（Liu et al., 2023）
- MT-Bench 评委偏差研究：长度、位置、自我偏好偏差（Zheng et al., 2023）
- RADAR (2026): rubric 维度行为耦合诊断，预检评分体系
- V-GameGym (上海 AI Lab, 2025): 游戏开发代码生成的客观+主观混合评测管线，强调可玩性、视觉表现等游戏特有指标
- RPG Bench (2025): 游戏相关评测中客观 checker 提供稳定基准、主观维度方差大的结论
- HalluLens: benchmark 设计准则——真实场景代表性、稳定性与敏感性、可复现性、抗污染
- LangChain / Arize / DeepEval 工程实践：程序化验证优先、golden dataset 校验评委（75-90% 一致率）、轨迹级评估
- 华为云盘古提示词最佳实践：结构化提示词、引号隔离参考文本防指令冲突
