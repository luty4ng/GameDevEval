# GameEval Studio 设计与实施报告

日期：2026-10-13 · 版本：1.0

## 1. 交付结论

已在 `Tools/game-eval-studio` 实现可本地运行的中文 WebApp，完成题目起草、需求编制、规则设计、质量检查、专家试评、冻结版本与交付导出的完整内容生产流程。调研与产品要求先写入 [PRD](PRD.md)，实现后的使用流程见 [操作指南](USER-GUIDE.md)。未改动 Unity 资产与工程配置，未提交或推送 Git，未发布外网。

首版是单机内容工作台，使用确定性模板起草。它不运行 coding agent、引擎测试或性能采样，不调用生成模型，试评证据由专家从外部执行结果录入。

## 2. 为什么这样设计

开源平台提供了三个可迁移的思想：Promptfoo 把用例与断言分开；Langfuse 把题目、实验、专家分数与评论分开；SWE-bench 强调基线与执行环境。游戏领域还需要视觉、场景、交互与运行时证据，[GameDevBench](https://github.com/waynchi/gamedevbench)、[GameCraft-Bench](https://github.com/FreedomIntelligence/gamecraft-bench)、[OpenGameEval](https://github.com/Roblox/open-game-eval) 的设计支持这一判断。完整事实出处和产品推断见 PRD 的调研表。

据此选择“需求 → 观察步骤 → 验收条件 → 关联规则 → 分数与证据”作为核心数据链。输入是游戏开发目标和环境；处理是模板起草、专家编辑和完整性检查；输出是可交给 agent 的公开任务与留给专家的评分规则。

没有把“生成一段好看的文案”当作内容生产完成。结构关联、采样条件、评分锚点、门槛和版本追溯共同决定评测是否可用。

## 3. 游戏开发领域建模

六类模板覆盖玩法逻辑、图形地形、战斗 AI、游戏 UI、性能优化和完整小游戏。它们共享构建/运行交付门槛，另外四条需求按领域编写。例如地形任务检查固定 seed、LOD 接缝、GPU 资源生命周期和 Player 性能；UI 任务检查堆叠数据、键盘焦点、多分辨率和生命周期。

环境字段固定引擎版本、平台、仓库基线、入口、seed、设备、时间、运行协议、工具/网络/资产限制。示例使用当前项目读取到的 Unity 6000.5.5f1；示例基线、设备和场景被校验器明确阻止用于正式冻结。

评分维度和执行方法分开：功能正确性是一种维度，自动化运行是一种方法。一个需求可以由多条规则从不同角度观察；一条规则也可以关联多个需求，但需避免重复奖励。

## 4. 评分与版本设计

规则包含五级具体锚点、百分比权重、证据要求与硬门槛。总分 `Σ(权重 × 评分 / 4)`；完整达标 3 分对应总分 75，重复验证稳定 4 分对应 100。任何硬门槛低于 3 分则不通过，否则按任务阈值判断。

评分结果分为待完成、通过、门槛失败与阈值失败。未评不记成零分；有分数但无证据仍待完成；题目定义不完整也不能得出正式结论。界面明确区分临时分和最终分。

试评与题目定义分开存储。编辑定义时清空旧试评；冻结版本复制完整 Task，保留确认人、说明和时间。后续草稿修改不会改变版本；旧版导出只读取快照，不拼接当前草稿试评。专家确认是本地内容审查记录，不是身份认证。

## 5. 软件结构与数据流

| 文件 | 职责 |
| --- | --- |
| `src/model.ts` | 类型、Zod 备份协议、需求与规则 ID |
| `src/templates.ts` | 六类模板和完整示例 |
| `src/domain.ts` | 质量校验、评分、编辑失效、快照、差异、导入校验 |
| `src/export.ts` | agent/专家文件分离、CSV、ZIP、SHA-256、下载 |
| `src/storage.ts` | 带版本的 localStorage 读取与损坏保护 |
| `src/App.tsx` | 题库、工作流、表单、自动保存、恢复与确认交互 |
| `src/styles.css` | 语义配色、桌面/窄屏布局与可访问状态 |
| `tests/domain.test.ts` | 领域约束与导出完整性测试 |
| `tests/e2e.py` | 真实浏览器端到端验证 |

创建流程：`NewTask → createProject → Workspace → 自动保存`。

编辑流程：`表单 → editTask → 清空旧试评 → validateTask → 保存`。

试评流程：`分数/证据 → Review → reviewSummary → 临时或正式结论`。

冻结与交付：`validateTask + 专家确认 → freezeVersion → 不可变快照 → packageFiles → SHA-256 → JSZip → 下载`。

导入流程：`文件大小限制 → JSON 解析 → Zod 结构 → ID/版本/试评引用检查 → 分配新任务 ID → 合并题库`。

输入中尚未完成的数值允许作为草稿保存，再由质量检查阻止冻结，避免用户清空输入框后刷新导致整份题库无法读取。试评分数等确定性数据仍严格限制。导入内容不执行代码，不解释 HTML。

## 6. 技术方案及代价

选用 React、TypeScript、Vite；Zod 校验协议，Lucide 图标，JSZip 打包。依赖版本由 `package-lock.json` 锁定，已在 Node 22.20.0 上验证。JSZip 在用户请求 ZIP 导出时动态加载，减少首次加载开销；不依赖外网字体、图片或分析服务。

纯前端适合当前“项目旁使用、单专家生产内容”的目标。服务端数据库更适合协作，但引入服务、登录和权限维护；首版用导出备份和导入交换承担移交。AI 起草可减少编辑量，但增加密钥、费用和幻觉校准；本次先提供可解释的本地模板。

localStorage 按浏览器源隔离；写入 400ms 去抖，离开页面时尽量补写最新数据；同源其他标签改动会暂停保存并提示恢复，避免静默覆盖。存储失败时显示未保存状态，损坏数据不覆盖，允许下载原始数据。这不是服务端备份或多人事务系统。

## 7. 交付隔离与可追溯性

agent 文件只包含任务、需求、公共运行条件与显式公开的规则；私有锚点、证据要求、完整规则与试评写入 expert 文件。完整包是专家交付物，运行时只向 agent 提供 `agent/`。CSV 有 UTF-8 BOM，转义引号与换行，并处理公式前缀，便于中文 Excel 使用。

manifest 记录任务、草稿/冻结状态、版本与导出时间，并列出每个内容文件的 SHA-256。哈希用于验证文件是否改变，不代表评测本身正确或专家身份可信。备份 JSON 与评测 ZIP 分离，避免用可执行侧资料误当工作区恢复文件。

## 8. 界面设计

界面采用编辑器式布局：深蓝题库导航、明亮主编辑区、青蓝操作色、右侧交付检查。主要信息是实际需求、规则和问题，不使用营销页或装饰性指标。主流程保持五个固定入口；问题能跳到对应字段或条目。

通过 `frontend-design` 和 `ui-ux-pro-max` 技能校准视觉。技能检索的样式建议适合密集工作台，但营销式页面结构不适合本任务，因此只采用信息密度、配色可读性和可访问规范；未照搬推荐首页。中文使用系统字体，保持离线可用。

表单使用独立可访问名称与提示描述；使用原生 dialog 做焦点管理；有跳过导航入口；主要状态都有文字；支持减少动效。窄屏题库改为可横向滚动的局部列表，工作区纵向排列；正文页面不产生水平溢出。

## 9. 实际验证结果

- `npm run build`：TypeScript 严格检查和 Vite 生产构建通过。
- `npm test`：30 项领域测试通过，涵盖六类模板、校验、门槛、证据、快照、历史 ID、导入与导出。
- `python tests/e2e.py`：18 项真实 Chromium 浏览器流程检查通过；本次复核针对生产构建的 `npm run preview`。
- 主流程无未处理 JavaScript 异常或控制台错误。
- 375 / 768 / 1024 / 1440 宽度下五个页面无文档横向溢出；减少动效、Esc 关闭与焦点恢复通过。
- 实际下载 ZIP 中 agent 文件无测试用私有标记，所有 manifest 哈希与 Python 读取的文件内容一致。
- 实际验证保存/刷新、立即刷新未填完数值、版本稳定、备份回导、坏格式拒绝、多标签冲突、损坏存储保留与容量失败提示。
- 初次依赖安装使用环境已有镜像时发生 npm peer 解析错误；改用官方 registry 后安装完成，未修改系统全局配置，安装当时 audit 为 0 漏洞。
- 可用性复核增加标签内任务/页签恢复、历史版本 ID 保留，以及存储读取被拒绝时的恢复反馈；补测搜索、复制和删除，全新 `npm ci` 成功。

测试产物保存在被忽略的 `test-results/`，包括 `e2e-report.json`、截图、真实下载的备份与 ZIP。报告截图使用隔离测试题库；不存在真实专家评分或实际游戏验证结果。

## 10. 边界与下一步
