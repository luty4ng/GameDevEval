# GameEval Studio 产品需求文档

版本：1.0 · 日期：2026-10-13 · 状态：首版实施基线

## 1. 产品结论

在本项目 `Tools/game-eval-studio` 中建设中文、本地优先的 WebApp，服务游戏开发专家，为 coding agent 生产可复用的开发需求列表和评测规则集。核心流程是：任务背景 → 模板草稿 → 原子需求 → 关联规则 → 质量检查 → 专家试评 → 冻结版本 → 导出交付。它是评测内容生产工具；实际运行 agent、启动游戏和采集性能数据由外部执行器完成。

现有 Unity 项目作为领域参考，首版以 Unity 为默认引擎，同时允许 Unreal、Godot、Web 和自定义引擎。Windows 现有目录实际名为 `Tools`，沿用它避免重复目录。保留项目已有文件和未提交改动。

## 3. 用户与问题

- 题目作者：将开放式游戏开发想法拆解成有限、独立、可验收需求，避免任务难度漂移。
- 游戏开发专家：制定标准，校准视觉、交互、性能与工程质量，并用证据解释扣分。
- 评测组织者：冻结题目与规则，将相同条件交给不同 agent，保留版本追溯。

主要痛点：需求含糊、规则无法映射需求、分值不闭合、性能无硬件条件、视觉无参考轨迹、构建失败仍获高分、隐藏测试泄漏、评审凭印象打分、修改后沿用旧分数。

## 4. 需求范围与优先级

### P0：本次交付

1. 题库管理：创建、复制、搜索、切换、删除任务；提供明确标识的完整示例。
2. 模板起草：至少覆盖玩法控制、战斗 AI、游戏 UI、图形地形、性能优化和完整小游戏；使用本地确定性模板，无 API key 或网络依赖。任务简述、难度和环境进入生成结果，不宣传为模型生成。
3. 任务规格：编辑名称、目标、引擎/版本、平台、仓库基线、场景、随机种子、时间预算、设备、运行协议、工具/网络/资产约束、交付物和通过阈值。
4. 原子需求：稳定 ID、名称、领域、优先级、描述、观察步骤、验收条件；增删编辑。删除有关联规则的需求前提示影响，删除后保留规则并提示悬空引用。
5. 规则集：稳定 ID、关联需求、维度、方法、权重、0–4 分锚点、证据要求、是否硬门槛、公开/私有。硬门槛需至少 3 分才通过。
6. 质量检查：环境必填、需求与规则字段、ID 唯一、关联完整、全部需求被覆盖、权重合计 100、至少一个构建/运行门槛、评分锚点完整。给出定位与修复入口；存在错误不能冻结正式版本。
7. 专家试评：填写评审人与匿名提交标识，逐条评分和证据；未评分或缺证据时仅展示已评分部分的临时得分，结论为待完成；记录变更使旧试评分失效。
8. 版本：专家填写确认人和评审说明，冻结不可变快照；继续改动草稿不修改旧版本；查看版本差异和下载指定版本。
9. 导出：草稿/正式版本 ZIP、agent task.md、需求 JSON/CSV、规则 JSON/CSV、评测 JSONL、protocol.md 和试评记录；ZIP 含带 SHA-256 的 manifest。私有规则仅写入专家文件。公开提示不暴露私有规则的锚点和证据协议。
10. 数据：浏览器自动保存，保存失败可见；JSON 备份、严格校验后导入为新任务；导出草稿始终可用；不执行导入的脚本、HTML 或命令。
11. 体验：中文、键盘可用、有标签/焦点、清晰空状态、窄屏可操作，桌面优先的编辑布局。

### P1：后续方向（本次不实现）

团队数据库与权限、双人盲评及仲裁、批量题目审核、与 Promptfoo/Langfuse 的运行 API 集成、LLM 辅助起草、证据附件存储、自动引擎运行器与性能采集、真实参考作品管理。首版交换格式是本工具自有协议，不声称直接兼容外部执行器。

## 5. 游戏开发专家评测协议

共同评测环境固定：引擎及依赖、仓库基线、运行场景、设备与分辨率、随机种子、输入序列、预热/采样方案、时间预算、允许工具/联网、合法资产来源。任务作者应消除“自行选设备”导致的性能比较误差。

维度包含功能正确性、可运行性、视觉表现、交互体验、稳定性、性能、工程质量。模板按任务选用维度与权重，不机械要求每题都测所有维度。

每条规则用五级锚点：0 未实现或无法验证；1 核心失败；2 部分达标；3 完整达到验收要求；4 达标且在明确边界/重复验证中稳定。锚点必须落到具体任务观察，不把额外无关功能奖励为满分。

总分 `Σ(权重 × 评分 / 4)`，权重总和 100。所有规则完成并有证据后才能出正式试评结论。硬门槛任一低于 3 分则不通过；否则按任务阈值判断。门槛未评则待完成。试评仅帮助校准规则，并不意味着应用已运行 Unity 或 agent。

避免偏差：提交标识使用匿名编号；视觉规则配固定操作路径；性能规则需采样条件；不以模型品牌、解释文风或代码长度加分；人工裁决优先于不可靠的文本 judge；隐藏规则不得引入公开需求之外的秘密功能要求。

## 6. 信息架构与界面

左侧：品牌、题库搜索、任务列表、本地存储提示、备份/导入、使用帮助。

主区：任务标题与状态 → 工作流页签（任务设定 / 需求列表 / 评测规则 / 专家试评 / 版本与导出）→ 页面正文。

需求与规则采用列表 + 就地编辑，规则显示需求关联。右侧就绪检查汇总覆盖、权重和缺失信息，并可跳转定位。版本页展示草稿预览、冻结操作、版本历史和差异。

视觉选择：冷灰工作台、深海蓝导航、青蓝操作色、小面积琥珀告警，界面以信息密度与编辑效率为中心；使用本地系统中文字体，无远程字体依赖。避免营销首页与装饰图表，选用真实覆盖关系和可解释校验结果。

## 7. 技术设计基线

React + TypeScript + Vite，纯前端。Zod 做导入结构校验，独立领域函数负责起草、验证、评分、导出和版本差异，JSZip 生产离线评测包，Vitest + Playwright 验证逻辑与真实界面。状态放在带 schemaVersion 的 localStorage，自动保存到当前浏览器当前源；备份 JSON 是跨设备与灾备手段。

选择纯前端是因为当前目标是单机生产题目，便于在 Unity 项目旁快速使用。服务端数据库能提供多人协作，但引入服务维护与权限工作，留到团队版。未接 LLM 避免模型臆造规则和密钥管理；需要模型辅助时可以导出任务给 coding agent 后导回结构化文件。

本地预览限定 loopback；不自动发布外网。应用数据留在用户浏览器，不读写 Unity 场景，不提交或推送 Git。

## 8. 验收标准

- 从模板新建题目，编辑需求和规则，刷新后内容仍在。
- 覆盖断裂、权重不是 100、缺环境、门槛缺失等被检查发现并阻止冻结。
- 未评与缺证据不被当成 0 分；门槛失败压过总分；修改内容清空旧试評。
- 冻结后改草稿，旧快照与旧导出保持一致；差异可见。
- agent 文件没有私有 rubric；专家文件包含全部规则；ZIP 校验和与文件内容一致。
- JSON 备份可回导；恶意或不合格式导入被拒绝且不覆盖原数据；CSV 公式开头被转义。
- 主要流程在真实浏览器通过，375px 和桌面无页面横向溢出，无未处理控制台错误。
- 项目交付 PRD、调研、设计报告、操作指南、源码与可复现测试命令。

## 9. 数据风险与边界

localStorage 是浏览器存储，不是服务端备份；清除浏览器数据、切换源或隐私窗口会使题库不可用，界面明确提示备份。容量失败时保持内存数据并提示下载备份，不声称保存成功。多标签同源写入通过外部变更提示防止静默覆盖。导出是用户触发下载，版本冻结只改变本地数据。

真实性边界：模板给出候选验收协议，不保证这些阈值在具体游戏中合理；专家必须按目标硬件和基线校准。证据字段存文本引用，不上传录屏；应用不检查被引用文件是否存在。
